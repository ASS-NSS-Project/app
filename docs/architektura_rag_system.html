Jak celý systém funguje — kompletní průvodce architekturou

Tento dokument popisuje systém, který automaticky stahuje obsah z webových stránek, zpracovává ho pomocí umělé inteligence a umožňuje uživatelům klást otázky nad tímto obsahem a dostávat odpovědi s přesnými citacemi na zdroj. Níže je vysvětlena každá část diagramu srozumitelným jazykem.

1 Co systém dělá

Představte si, že máte stovky webových stránek, ze kterých potřebujete pravidelně získávat informace — novinky, tabulky, dokumenty, statistiky. Ručně by to zabralo hodiny. Tento systém to dělá automaticky:

  1. Stáhne obsah z webu — navštíví stránku, přečte její obsah, a pokud je stránka příliš složitá (animace, JavaScript, složité tabulky), pořídí její screenshot a obsah „přečte" z obrázku pomocí AI.
  2. Zpracuje a uloží — vytvoří strukturovaný dokument (nadpisy, odstavce, tabulky) a uloží ho spolu s důkazem (screenshot, originální HTML), aby bylo vždy možné ověřit, odkud informace pochází.
  3. Umožní se ptát — uživatel napíše dotaz (např. „Jaké byly hlavní závěry zprávy XY?") a systém pomocí AI najde relevantní části dokumentů a vygeneruje odpověď s přesnými citacemi.

Technicky se jedná o tzv. RAG systém (Retrieval-Augmented Generation) — AI model negeneruje odpovědi „z hlavy", ale nejprve vyhledá relevantní pasáže v uložených dokumentech a odpověď postaví na nich. Díky tomu jsou odpovědi ověřitelné a minimalizují se „halucinace" (vymyšlené informace).

2 Uživatelská vrstva — fialová zóna

Toto je ta část systému, se kterou přímo pracuje člověk.

🖥 Web UI (Vue 3 + TypeScript)

Webová aplikace, kterou uživatel otevře v prohlížeči. Přes ni se přihlásí, zadává dotazy, prohlíží odpovědi s citacemi, a pokud má roli správce zdrojů, může přidávat nové webové stránky ke sběru. Aplikace je postavena na frameworku Vue 3 s programovacím jazykem TypeScript, což jsou moderní nástroje pro tvorbu rychlých a spolehlivých webových rozhraní.

🔐 Auth / Keycloak (přihlášení)

Keycloak bude sloužit jako centrální Identity Provider (IdP) pro celý systém. Aplikace (frontend + FastAPI backend) budou využívat standardní OIDC (OpenID Connect) flow — uživatel se přihlásí přes Google účet, Keycloak vydá JWT token, backend ověří podpis tokenu a přidělí roli (administrátor, kurátor, analytik, běžný uživatel).

Interní nástroje infrastruktury, které nativně OIDC nepodporují (Grafana, RabbitMQ Management UI, Qdrant Web UI, Prometheus aj.), budou chráněny pomocí vzoru Forward Authentication na úrovni reverzní proxy. Traefik forwardAuth middleware (resp. NGINX Ingress anotace auth-url) bude každý příchozí požadavek před předáním službě ověřovat prostřednictvím instance oauth2-proxy, která validuje session vůči Keycloaku jako upstream IdP. Tímto způsobem lze vynutit jednotné přihlášení (SSO) pro libovolnou interní službu bez nutnosti její modifikace.

📋 Audit log

Každá akce v systému se zaznamenává — kdo se přihlásil, kdo položil jaký dotaz, kdo změnil nastavení zdroje. Tyto záznamy se ukládají do databáze PostgreSQL a slouží pro bezpečnostní audit a řešení případných incidentů.

3 API Gateway + proxy — modrá zóna

⚡ REST API (FastAPI)

Veškerá komunikace mezi webovým rozhraním a zbytkem systému probíhá přes tzv. API (Application Programming Interface). Je to sada pravidel, která říká „pokud chceš položit dotaz, pošli požadavek na tuto adresu v tomto formátu". Používáme framework FastAPI (Python), který je rychlý a automaticky generuje dokumentaci ke všem dostupným příkazům.

🔀 Reverse proxy (Traefik / NGINX Ingress)

Reverse proxy je „vrátný" systému — stojí na vstupu, přijímá všechny příchozí požadavky z internetu, šifruje spojení (HTTPS) a přesměrovává je na správnou interní službu. V MVP fázi používáme Traefik, v produkčním Kubernetes prostředí pak NGINX Ingress nebo Traefik dle konfigurace clusteru. TLS certifikáty (šifrování) se získávají automaticky od Let's Encrypt přes nástroj cert-manager. V prostředí CERIT-SC Kubernetes je k dispozici předkonfigurovaný letsencrypt-prod ClusterIssuer, takže certifikáty se vydávají automaticky. → Dokumentace CERIT-SC: Certifikáty

4 Backend — pipeline a orchestrace — zelená zóna

Toto je „továrna" systému — místo, kde se obsah stahuje, zpracovává a připravuje pro vyhledávání. Obsahuje několik specializovaných komponent:

🎯 Orchestrátor (Prefect / Temporal)

Řídí celý pracovní postup (workflow). Plánuje, kdy se má stáhnout obsah z kterého zdroje, zajišťuje, že pokud nějaký krok selže, automaticky se zopakuje (retry), a koordinuje pořadí operací. Funguje jako „dispečer" celé továrny.

📬 Queue / fronta (RabbitMQ)

Fronta zpráv, která odděluje jednotlivé kroky zpracování. Když orchestrátor řekne „stáhni tuto stránku", vloží zprávu do fronty a příslušný worker ji převezme. Díky tomu může systém zpracovávat více stránek najednou a nezahltí se. RabbitMQ je osvědčený open-source systém pro řízení front zpráv.

🚨 Incident manager (CAPTCHA)

Některé webové stránky zobrazí CAPTCHA (ověření „nejsi robot") nebo jinou překážku. Systém takovou situaci automaticky detekuje, uloží důkaz (screenshot stránky s CAPTCHA), zapíše incident a zařadí ho do fronty pro vyřešení kurátorem. Po vyřešení se automaticky doplní chybějící data.

🔄 Ingest workers — multimodální fallback řetězec

Toto je klíčová inovace systému. Každý zdroj (webová stránka) se stahuje pomocí řetězce strategií, kdy pokud jedna selže, automaticky se zkusí další:

  1. API/Feed — pokud web nabízí strukturované rozhraní (API, RSS), použije se to (nejlepší kvalita).
  2. HTML fetch + parse — stáhne se HTML kód stránky a obsah se extrahuje ze zdrojového kódu.
  3. Rendered DOM (Playwright) — stránka se otevře v plném prohlížeči (jako by ji otevřel člověk), nechá se načíst JavaScript, a pak se přečte výsledný obsah. Playwright je nástroj od Microsoftu pro automatizaci prohlížeče.
  4. Screenshot screening — pokud ani renderovaný DOM nestačí (např. obsah v canvasu nebo složitém layoutu), pořídí se snímek celé stránky a AI model z obrázku extrahuje text, nadpisy a tabulky.
  5. Upstream AI provider — jako poslední možnost se použije komerční AI služba, která obsah zpracuje za nás.

👁 AI extraktor (Qwen2.5-VL-7B)

Když se pořídí screenshot stránky, tento AI model „přečte" obrázek — rozpozná text (OCR), identifikuje nadpisy, odstavce, tabulky, a odstraní navigační prvky a reklamy. Model Qwen2.5-VL-7B je open-source „vision-language" model, který rozumí jak textu, tak obrázkům, a dobře zvládá češtinu. Běží lokálně na GPU kartě (nepotřebuje internet).

📄 Normalizer + ✂ Chunking engine

Normalizer vytvoří ze stažených dat jednotný formát dokumentu (nadpis, sekce, tabulky, metadata) a detekuje duplicity. Chunking engine pak tento dokument rozřeže na menší kousky (chunky) optimální velikosti pro vyhledávání — typicky několik odstavců. Velikost a překryv chunků jsou konfigurovatelné pro ladění kvality vyhledávání.

📂 Source registry

Registr všech zdrojů — každá webová stránka má záznam s URL adresou, pravidly sběru (jak často, jak hluboko), právním titulem (povolení ke stahování) a retenčními pravidly (jak dlouho uchovávat data).

5 AI služby — růžová zóna

Sada komponent, které provádějí samotnou „inteligentní" práci — vyhledávání v dokumentech a generování odpovědí.

🧮 Embedding service (BGE-M3)

Každý chunk dokumentu se převede na tzv. embedding — vektor čísel, který reprezentuje jeho význam. Podobné texty mají podobné vektory. Díky tomu může systém rychle najít chunky, které se významově nejvíce blíží zadanému dotazu. Model BGE-M3 je multilingvální (podporuje češtinu) a produkuje jak dense (husté), tak sparse (řídké) vektory — oba typy se doplňují pro přesnější vyhledávání.

🤖 LLM inference — lokální (llama.cpp / Ollama — zatím nerozhodnuto)

LLM (Large Language Model) je velký jazykový model — AI, která rozumí textu a generuje odpovědi. Lokální modely poběží přímo na serverech projektu, bez odesílání dat třetím stranám. Jako inference engine se zvažují dvě možnosti:

llama.cpp je nízkoúrovňový, vysoce optimalizovaný engine pro běh kvantizovaných modelů (GGUF formát) na GPU. Nabízí maximální kontrolu nad parametry inference (batch size, GPU layers, context length) a nejnižší overhead. HTTP server s OpenAI-kompatibilním API je dostupný, ale vyžaduje ruční správu modelů a konfiguraci. Vhodné pro produkční nasazení nebo prostředí HPC (MetaCentrum PBS joby), kde neexistuje persistentní démon.

Ollama je nadstavba nad llama.cpp poskytující OpenAI-kompatibilní REST API, automatickou správu modelů (ollama pull), detekci GPU a jednoduchou konfiguraci. Výrazně snižuje čas potřebný k zprovoznění inference služby a usnadňuje integraci — jakýkoliv klient OpenAI SDK funguje bez úprav. Mírně vyšší overhead oproti čistému llama.cpp. S ohledem na časový rozsah projektu (jeden semestr) se Ollama jeví jako pragmatičtější volba, finální rozhodnutí bude učiněno v průběhu fáze Konstrukce.

Primární model bude Llama 3.3 70B (Q4_K_M, ~40 GB VRAM), alternativně Qwen2.5-72B pro silnější výkon v češtině a lehčí Mistral Small 3.1 24B pro rychlejší odpovědi.

☁ LLM inference — upstream API

Pro srovnání kvality a jako záložní řešení systém podporuje i komerční AI služby: Anthropic Claude (Opus/Sonnet), Google AI Studio (Gemini) a OpenAI (GPT-4o/GPT-4.1). Tyto modely jsou výkonnější, ale vyžadují připojení k internetu a platbu za použití. Systém může porovnávat kvalitu odpovědí lokálních a komerčních modelů.

🧪 Experiment engine

Nástroj pro systematické testování a porovnávání kvality vyhledávání a odpovědí. Analytik může spustit experiment — například porovnat dva různé embedding modely, nebo srovnat odpovědi v režimu RAG vs. bez RAG. Systém automaticky vyhodnotí metriky jako Recall@k (kolik relevantních dokumentů bylo nalezeno), MRR (jak vysoko byl relevantní dokument v pořadí) a nDCG (kvalita řazení). Výsledky se vygenerují jako automatizovaný report.

6 Datové úložiště — oranžová zóna

Všechna data systému se ukládají do pěti specializovaných úložišť. Každé má svůj účel:

🗃 Evidence store (S3 — Ceph / MinIO / Garage)

Úložiště důkazů — screenshoty stránek, stažené HTML a PDF soubory, DOM snapshoty. Každý důkaz má hash (digitální otisk), takže je možné ověřit, že nebyl pozměněn. Technicky jde o S3-kompatibilní objektové úložiště — stejný standard, který používá Amazon Web Services, ale provozovaný lokálně. V produkci lze využít CESNET S3 storage nebo MinIO Operator na Kubernetes. → Dokumentace CESNET: S3 Object Storage · → CERIT-SC: MinIO Operator

🗄 Metadata DB (PostgreSQL)

Relační databáze, kde se uchovává vše strukturované — registr zdrojů, stav zpracování, verze dokumentů, záznamy incidentů, audit log, konfigurace rolí. PostgreSQL je nejpopulárnější open-source databáze na světě. Na Kubernetes se nasazuje přes CloudNative-PG Operator, který automatizuje zálohy, replikaci a aktualizace. → CERIT-SC: Postgres Operator

🔍 Vector DB (Qdrant)

Specializovaná databáze pro vektorové vyhledávání. Ukládá embedding vektory (číselné reprezentace textu) a umožňuje extrémně rychle najít nejpodobnější dokumenty k zadanému dotazu. Qdrant podporuje filtrování podle metadat (např. „hledej jen v dokumentech z posledního měsíce ze zdroje X") a umožňuje snapshoty pro zálohy a rollback indexu.

📑 Fulltext index — VOLITELNÝ (OpenSearch)

Doplňkový index pro tzv. hybrid retrieval — kombinace vektorového vyhledávání s klasickým fulltextovým vyhledáváním (BM25). Pro některé typy dotazů (přesné fráze, kódy, čísla) je fulltextové vyhledávání přesnější než čistě vektorové. OpenSearch je open-source alternativa Elasticsearch. Tato komponenta není povinná — systém funguje i bez ní, ale pokud je nasazena, zlepšuje kvalitu vyhledávání.

🔑 Config store (HashiCorp Vault)

Bezpečné úložiště tajemství — API klíče k AI službám (Anthropic, Google, OpenAI), přístupové údaje k databázím a S3, mTLS certifikáty pro zabezpečenou komunikaci mezi interními službami, a Keycloak client secrets. Vault zajišťuje, že hesla a klíče nejsou nikdy uložena v otevřené podobě v kódu nebo konfiguračních souborech. Na Kubernetes se alternativně používají Sealed Secrets.

7 Monitoring a logy — šedá zóna

Monitoring zajišťuje, že víme, co se v systému děje, a jsme upozorněni, když se něco pokazí.

📈 Prometheus + 📜 Loki → 🔔 Alertmanager → ✈ Telegram

Prometheus sbírá číselné metriky ze všech služeb (kolik stránek se stáhlo za minutu, jaká je latence odpovědí, kolik chyb nastalo). Loki sbírá textové logy (záznamy událostí). Oba systémy mají pravidla, která definují, kdy má vzniknout alert — např. „pokud error rate překročí 5 %, upozorni nás". Tyto alerty směřují do Alertmanageru, který je seskupí, deduplikuje a odešle notifikaci do Telegram chatu projektového týmu přes Telegram Bot API.

Typy alertů zahrnují: selhání stahování, detekce CAPTCHA, přeplnění fronty, výpadek databáze, vysoká latence AI modelu, a překročení chybovosti.

📊 Grafana + 🔧 Alloy

Grafana je webový dashboard, kde tým vidí v reálném čase stav celého systému — grafy, tabulky, trendy. Alloy (Grafana Alloy) je agent, který běží na každém serveru a sbírá logy a metriky ze všech kontejnerů, a posílá je do Loki a Prometheus.

8 Nasazení — e-INFRA CZ infrastruktura — modrá zóna

Celý systém běží na infrastruktuře e-INFRA CZ — národní výzkumné infrastruktuře poskytující výpočetní zdroje akademické komunitě v ČR. Systém využívá tři hlavní služby:

🐳 MVP — Docker Compose na OpenStack Cloud (Horizon)

Pro první funkční verzi (MVP) se systém nasadí jako sada Docker kontejnerů na virtuálním serveru v e-INFRA CZ OpenStack Cloud (G2 Brno nebo Ostrava). OpenStack je platforma pro správu virtuálních serverů — přes webové rozhraní Horizon si vytvoříte server s požadovanými parametry (CPU, RAM, GPU) a na něm spustíte celou aplikaci. Reverse proxy v MVP fázi je Traefik.

→ Dokumentace: e-INFRA CZ OpenStack Cloud

☸ Produkce — Kubernetes na CERIT-SC (Rancher)

Pro produkční nasazení se systém přesune na CERIT-SC Kubernetes platformu — managed Kubernetes cluster spravovaný přes Rancher dashboard. Kubernetes automaticky zajistí, že když služba spadne, restartuje se; když je příliš zatížená, spustí se další instance (horizontální škálování). Na platformě jsou k dispozici GPU akcelerátory (NVIDIA L40, L40S, T4), operátory pro MinIO (S3 storage) a CloudNative-PG (PostgreSQL), a automatické TLS certifikáty přes cert-manager.

⚡ Batch / AI výpočty — MetaCentrum Grid (PBS)

Náročné výpočty (přepočet embeddingů pro tisíce dokumentů, experimenty s různými modely, rebuild indexů) se odesílají jako dávkové úlohy do MetaCentrum Grid — superpočítačové infrastruktury s PBS scheduler. K dispozici jsou GPU clustery: alfrid (NVIDIA L40/L40S 48GB — ideální pro běh 70B modelů), DGX H100 (8× H100 80GB — pro nejtěžší úlohy), a řada clusterů s Tesla T4 16GB pro embedding a VLM extrakci. Výpočty běží v Singularity kontejnerech (obdoba Dockeru pro HPC prostředí) s přístupem k NGC obrazům přes CVMFS.

Systém může také využít CERIT-SC AI-as-a-Service — OpenAI-kompatibilní API pro přístup k lokálně běžícím LLM modelům na infrastruktuře e-INFRA bez nutnosti vlastních GPU.

9 Role a oprávnění (RBAC)

Systém rozlišuje čtyři role, z nichž každá má jiná oprávnění:

Role Co může dělat Typický uživatel
🛡 Administrátor Správa uživatelů a rolí, systémové nastavení, retenční politiky, přístup k Vault tajemstvím Správce systému
📋 Kurátor Přidávání zdrojů (webů) ke sběru, doložení právního titulu/licence, nastavení pravidel sběru (frekvence, hloubka), řešení CAPTCHA incidentů Datový knihovník
🧪 Analytik Spouštění experimentů (A/B testy embeddingů, RAG vs. no-RAG), správa testovacích datasetů dotazů, prohlížení automatizovaných reportů Výzkumník, data scientist
💬 Standardní uživatel Zadávání dotazů, volba režimu dotazování (RAG/no-RAG), prohlížení odpovědí s citacemi a evidence Koncový uživatel

Všichni uživatelé se přihlašují přes Keycloak (Google login). Role se dědí od společného předka „Systémový uživatel".
