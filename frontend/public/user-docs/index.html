Query all users

The Query page is the default landing page for every authenticated user. It lets you ask natural-language questions against the indexed knowledge base and receive answers with citations.

How it works

Your question is embedded with the local BGE-M3 model, run against Qdrant using hybrid vector search (dense + sparse with RRF fusion), and the retrieved chunks are passed together with your question to the configured LLM. The answer is returned alongside citations — each one links to the source URL and shows the relevance score of the retrieved chunk.

Query modes

ModeWhen it is usedUI indicator
ragNormal operation — retrieves indexed chunks first, then generates the answerBlue "RAG" tag
no_ragCalls the LLM directly without any indexed contextGray "NO_RAG" tag
keyword_fallbackAutomatic fallback when Qdrant is unavailable — uses Postgres full-text search insteadOrange "KEYWORD SEARCH" tag and a warning banner

Options

  • Model — choose from the LLM providers configured on the server.
  • Strict grounding — when on, the LLM is instructed to answer only from the retrieved chunks, not from its training data.
  • Source filter — restrict retrieval to a single indexed source.
  • top_k — number of chunks to retrieve (default 5).
Note: Documents are keyword-searchable immediately after ingest. Vector search (better relevance) becomes available 1–5 minutes later, once the embedding worker finishes processing.

Knowledge Base admin · curator · analyst

Browse, search, and inspect all documents that have been ingested into the system.

What you can do

  • Search documents by title or URL.
  • Filter by source to see only documents from one monitored URL.
  • Open a document to read its extracted markdown.
  • Expand the Chunks panel to see the individual text segments indexed in Qdrant.
  • Download the raw markdown via a pre-signed S3 link.
  • Delete a document — also removes its chunks and Qdrant vectors.

Chunk types

TypeDescription
textProse paragraphs split at token boundaries
tableTable content extracted from the page
blockStructured blocks extracted by the VLM (screenshot) strategy

Sources admin · curator

Sources are the URLs WebRAG monitors and periodically scrapes. Each source is ingested on a configurable schedule and its content is stored in the knowledge base.

Scraping strategies

StrategyHow it worksBest for
apiJina.ai reader API + RSS/Atom feed fallback → markdownNews feeds, clean article pages
htmlRaw HTTP fetch + BeautifulSoup + markdownifySimple static pages
renderedPlaywright headless browser, full DOM + markdownifyJavaScript-heavy pages
screenshotPlaywright screenshot + VLM text extractionPages where the HTML is unparseable

The system tries the preferred strategy first. If the extracted text is below the quality threshold (200 characters), it falls back to the next strategy in the chain. A CAPTCHA or block page detected at any step automatically creates an Incident.

Crawl frequency

Each source has a crawl frequency in hours. The scheduler checks every 5 minutes for sources that are due and queues an ingest job automatically.

SSRF protection: URLs pointing to private, loopback, or link-local addresses are rejected by the backend.

Pipeline admin · curator

The Pipeline page shows the history of all ingest jobs across all sources. Each row represents one scrape attempt and its outcome.

Job statuses

StatusMeaning
pendingQueued in RabbitMQ, not yet picked up by a worker
runningWorker is actively processing the job
doneScrape succeeded; content stored to S3 and Postgres
failedAll strategies exhausted without extracting usable content
captcha_blockedCAPTCHA or block page detected; an Incident was created

Strategy fallback chain

For each job the page shows four steps in order: API/Feed → HTML → Rendered → Screenshot+VLM. Steps are marked as the one that succeeded, skipped (if a later strategy was selected directly), or failed.

Ingest timing

  • Ingest phase (~30 s) — scrapes the page, splits into chunks, stores to S3 and Postgres. Content is keyword-searchable immediately.
  • Embedding phase (1–5 min, background) — the embedding worker runs BGE-M3 and upserts dense + sparse vectors to Qdrant. Vector search activates after this phase.

Incidents admin · curator

An incident is created automatically when the ingest worker detects a CAPTCHA, rate-limit page, or access block during scraping. This page lets you review and resolve them.

Incident statuses

StatusMeaning
openDetected, not yet reviewed — shown as a red badge in the sidebar
in_progressUnder investigation
resolvedClosed manually or by a successful subsequent ingest

Resolving an incident clears the badge count in the sidebar. Admins can also create a synthetic test incident to verify that CAPTCHA detection is working correctly.

Experiments admin analyst

Experiments run batch query benchmarks against the knowledge base to measure retrieval quality. Each experiment defines a set of test queries with expected keywords and computes standard information-retrieval metrics.

Metrics

MetricDescription
Recall@kFraction of relevant chunks found in the top-k results
MRRMean Reciprocal Rank — how highly the first relevant result is ranked
nDCGNormalized Discounted Cumulative Gain — ranking quality weighted by position
Avg latency (ms)Mean end-to-end query time across all test queries
Note: The Experiments feature is currently scaffolded. The models and services are in place; the full UI workflow will be exposed in a future release.

REST API Access all users

Every authenticated user can generate a personal long-lived API token for programmatic access to WebRAG from scripts and terminals.

Generating a token

  1. Open REST API Access in the sidebar.
  2. Click Obtain API Token.
  3. Copy the token immediately — it is shown exactly once. The server stores only its SHA-256 hash and cannot retrieve the plaintext again.
  4. If the token is lost, click Regenerate to issue a new one (the previous token is immediately invalidated).

Tokens expire after 90 days. Authenticate requests with a Bearer header:

Authorization: Bearer <your-token>

Key endpoints

MethodPathPurpose
GET/healthLiveness check (no auth required)
GET/auth/meValidate token and return your profile
GET/sources/List monitored sources
POST/query/Ask a RAG question
GET/documents/Browse indexed documents
POST/sources/{id}/ingestTrigger an immediate ingest (curator and above)

Example

curl -s -X POST https://webrag.nss.jkzl.eu/api/query/ \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"question":"What sources are indexed?","mode":"rag","top_k":5,"strict_grounding":true}'

In production, prefix all paths with /api (e.g. /api/query/). Traefik strips the prefix before forwarding to the backend. In local development use paths directly against http://localhost:8000.

Dashboard admin · curator · analyst

The Dashboard link opens the WebRAG Overview Grafana dashboard in a new tab. It shows live system metrics: active sources, Qdrant collection size, open incidents, total ingest jobs, a 24-hour activity bar chart, and a strategy distribution breakdown.

Production only. The Grafana dashboards are part of the Kubernetes monitoring stack and are not available in local Docker Compose development.

Audit Logs & Access Control admin only

Audit Logs

Opens the WebRAG Audit Logs Grafana dashboard in a new tab. Every significant action — logins, source changes, ingest triggers, API token generation — is immutably recorded in the audit_logs table and surfaced here through Loki log panels.

Access Control

Opens the Keycloak Admin Console in a new tab. User accounts, group membership, and role assignments are managed there. Roles map as follows:

Keycloak groupRoleAccess
webrag_adminAdminAll pages and admin actions
webrag_curatorCuratorSources, Pipeline, Incidents, Query, Knowledge Base, REST API
webrag_analystAnalystQuery, Knowledge Base, Experiments, REST API
webrag_userUserQuery and REST API only

Role changes take effect on the user's next login, or automatically if the frontend detects a mismatch and refreshes the JWT (checked every 30 seconds while logged in).
