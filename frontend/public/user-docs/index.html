WebRAG uživatelská dokumentace

WebRAG je aplikace pro dotazování nad uloženými webovými zdroji. V běžném použití se přihlásíte, položíte otázku a odpověď dostanete společně s odkazy na části dokumentů, ze kterých systém vycházel.

Jak se přihlásit všichni uživatelé

Na přihlašovací stránce jsou podle nastavení serveru dostupné jeden nebo dva způsoby přihlášení.

Přihlášení přes OIDC / Keycloak

  1. Klikněte na Sign in with OIDC.
  2. Prohlížeč vás přesměruje do Keycloaku.
  3. Pokud Keycloak zobrazí volbu Google, klikněte na ni.
  4. Přihlaste se svým běžným účtem.
  5. Po úspěšném přihlášení se vrátíte zpět do WebRAGu.

Tento způsob je určen pro běžné uživatele. Trvání přihlášení se řídí nastavením Keycloaku.

Lokální first-admin přihlášení

Lokální heslo slouží hlavně pro první nastavení nebo nouzovou administraci. Zadává se pouze heslo, ne uživatelské jméno. Toto přihlášení je jen pro aktuální relaci prohlížeče.

Role a co uvidíte

RoleCo může dělat
webrag_userDotazování v Query a vlastní REST API token.
webrag_analystQuery, Knowledge Base, Experiments a REST API.
webrag_curatorSpráva zdrojů, pipeline, incidenty, Knowledge Base, Query a REST API.
webrag_adminVšechny funkce včetně auditních logů, Keycloak administrace a mazání vybraných záznamů.

REST API Access všichni uživatelé

REST API token použijete, pokud chcete WebRAG volat ze skriptu, terminálu nebo jiného nástroje. V aplikaci otevřete REST API Access, klikněte na Obtain API Token a token si hned uložte.

  • Token se zobrazí pouze jednou.
  • Server ukládá pouze jeho hash, ne čitelnou hodnotu.
  • Když token ztratíte, použijte Regenerate. Starý token se tím zneplatní.
  • Token posílejte v hlavičce Authorization: Bearer <WEBRAG_API_TOKEN>.
export WEBRAG_URL="https://webrag.example.com"
export WEBRAG_API_TOKEN="paste-token-here"

V příkladech níže nahraďte WEBRAG_URL adresou vaší instalace. Pokud je ve vašem prostředí API vystavené pod prefixem /api, přidejte ho před cestu endpointu.

Kontrola přístupu

curl -s "$WEBRAG_URL/auth/me" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"

Query všichni uživatelé

Query je hlavní obrazovka pro pokládání otázek. V RAG mode systém nejdřív najde relevantní části uložených dokumentů a teprve potom z nich připraví odpověď. Odpověď doplní citacemi, abyste viděli, odkud informace pochází.

Režimy v rozhraní

RežimKdy se používá
RAG modeBěžný režim. Hledá v uložených dokumentech a odpovídá s citacemi.
No RAG modeModel odpoví bez hledání ve znalostní bázi. Hodí se pro porovnání.

Automatická záloha vyhledávání

keyword_fallback znamená, že WebRAG dočasně použil jednodušší textové vyhledávání, protože běžné vyhledávání nebylo dostupné nebo nenašlo dost podkladů. Odpověď může být méně přesná, proto vždy zkontrolujte citace.

Důležité volby

  • Strict Grounding říká modelu, aby odpovídal pouze z nalezených dokumentů. Pokud je vypnutý, odpověď je volnější a model může přidat obecné znalosti mimo nalezené dokumenty.
  • top_k je API parametr pro počet nalezených částí dokumentů. Výchozí hodnota je 5. Vyšší číslo dává modelu více podkladů, ale odpověď může být pomalejší.
  • source_id je API parametr pro omezení dotazu jen na jeden zdroj.

Výběr poskytovatele modelu

Ve výchozím stavu WebRAG používá model nastavený na serveru. Pokud potřebujete jednorázově vyzkoušet jiný kompatibilní model, otevřete v Query část Pass Values for Your Own API.

  • Provider může být Default, OpenAI nebo OpenRouter.
  • Base URL je adresa API poskytovatele. Tlačítko nápovědy nabízí předvyplněné příklady.
  • API Key se použije jen pro aktuální požadavek a neukládá se.
  • Model Name je přesný název modelu u poskytovatele, například gpt-5.5 nebo openrouter/auto.

Stejné nastavení lze poslat přes API poli upstream_provider, upstream_base_url, upstream_api_key a upstream_model.

Po přidání nových dokumentů může chvíli trvat, než se začnou plně používat v odpovědích.

API příklad: položit otázku v RAG mode

curl -s -X POST "$WEBRAG_URL/query/" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "question": "What sources are indexed?",
    "mode": "rag",
    "top_k": 5,
    "strict_grounding": true,
    "source_id": null
  }'

API příklad: odpověď v No RAG mode

curl -s -X POST "$WEBRAG_URL/query/" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"question":"Explain what WebRAG is.","mode":"no_rag","top_k":5,"strict_grounding":false}'

API příklad: vlastní poskytovatel modelu

curl -s -X POST "$WEBRAG_URL/query/" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "question": "Summarize the newest indexed source.",
    "mode": "rag",
    "top_k": 5,
    "strict_grounding": true,
    "upstream_provider": "openai",
    "upstream_base_url": "https://api.openai.com/v1",
    "upstream_api_key": "paste-provider-key-here",
    "upstream_model": "gpt-5.5"
  }'

Knowledge Base admin / curator / analyst

Knowledge Base ukazuje dokumenty, které už WebRAG stáhl a rozdělil na menší části nazývané chunks. Každý chunk může být použit jako podklad pro odpověď v Query.

Co zde uvidíte

  • Počet dokumentů, chunků, zdrojů a procento chunků připravených pro RAG mode.
  • Tabulku dokumentů s URL, použitou ingest strategií, kvalitou a časem vložení.
  • Detail chunků pro konkrétní dokument.
  • Odkaz na uložený Markdown dokument nebo screenshot evidence, pokud existuje.

Admin a curator mohou dokument smazat. Smazání odstraní dokument a jeho části z vyhledávání.

API příklady

curl -s "$WEBRAG_URL/documents/stats" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"
curl -s "$WEBRAG_URL/documents/?limit=20&offset=0" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"
curl -s "$WEBRAG_URL/documents/DOCUMENT_ID/chunks" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"
curl -s "$WEBRAG_URL/documents/DOCUMENT_ID/markdown-url" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"

Sources admin / curator

Source je webová stránka nebo feed, který má WebRAG pravidelně sledovat. U zdroje nastavujete název, URL, typ oprávnění, preferovanou ingest strategii a frekvenci kontroly.

Ingest strategie

StrategieVysvětlení
apiNejdříve zkusí Jina.ai reader a RSS/Atom feed. Dobré pro články a čistý obsah.
htmlStáhne běžné HTML bez spouštění JavaScriptu. Rychlé pro jednoduché stránky.
renderedOtevře stránku v headless prohlížeči. Vhodné pro stránky závislé na JavaScriptu.
screenshotUdělá screenshot a nechá text přečíst vizuálním modelem. Nejdražší záloha pro složité stránky.

API příklady

curl -s "$WEBRAG_URL/sources/?limit=25" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"
curl -s -X POST "$WEBRAG_URL/sources/" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Example source",
    "base_url": "https://example.com",
    "permission_type": "public",
    "preferred_strategy": "api",
    "crawl_frequency_hours": 24
  }'
curl -s -X PATCH "$WEBRAG_URL/sources/SOURCE_ID" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"preferred_strategy":"rendered","crawl_frequency_hours":12}'

Pipeline / Jobs admin / curator

Pipeline ukazuje práci ingest systému: čekající úlohy, běžící workery, chybovost za posledních 24 hodin a historii jednotlivých jobů. Job je jeden pokus stáhnout a zpracovat konkrétní URL.

Stavy jobů

StavVýznam
pendingJob čeká ve frontě.
runningWorker job právě zpracovává.
doneObsah byl úspěšně uložen.
failedZpracování selhalo nebo bylo zrušeno.
captcha_blockedWeb ukázal CAPTCHA nebo blokaci; vznikne incident.

Job můžete ručně spustit ze Sources nebo přes API. Pending/running job lze zrušit. Admin může mazat dokončené job záznamy.

API příklady

curl -s "$WEBRAG_URL/sources/pipeline/stats" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"
curl -s "$WEBRAG_URL/sources/jobs/all?limit=20&status=failed" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"
curl -s -X POST "$WEBRAG_URL/sources/SOURCE_ID/ingest" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"url":"https://example.com/specific-page"}'
curl -s -X POST "$WEBRAG_URL/sources/jobs/JOB_ID/cancel" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"

Incidents admin / curator

Incident vznikne, když scraper narazí na CAPTCHA, rate limit nebo jinou blokaci. Cílem není blokaci obejít, ale dát člověku jasně vědět, že zdroj vyžaduje kontrolu.

Práce s incidentem

  • Resolve uzavře incident s poznámkou a automaticky zařadí nový retry job.
  • Whitelist v UI je rychlá varianta resolve s předvyplněnou poznámkou.
  • Admin může vytvořit testovací incident přes API endpoint /incidents/simulate.

API příklady

curl -s "$WEBRAG_URL/incidents/?status=open&limit=20" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"
curl -s -X POST "$WEBRAG_URL/incidents/INCIDENT_ID/resolve" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"resolution_note":"Checked the source; access is available again."}'
curl -s -X POST "$WEBRAG_URL/incidents/simulate" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"url":"https://example.com/captcha-test","severity":"medium"}'

Experiments admin / analyst

Experiments jsou připravené jako budoucí obrazovka pro porovnávání kvality odpovědí. V aktuální verzi je ve frontendu zatím placeholder a backend endpointy nejsou implementované.

Smyslem je vzít sadu testovacích otázek a změřit, jestli WebRAG našel správné podklady rychle a ve správném pořadí.

  • Recall@k říká, kolik správných podkladů se dostalo do krátkého seznamu výsledků. Je to podobné jako ověřit, jestli jste z regálu vytáhli všechny důležité knihy.
  • MRR sleduje, jak brzy se objeví první dobrý výsledek. Nejlepší stav je, když je první hned nahoře.
  • nDCG měří, jestli jsou nejlepší výsledky seřazené nahoře, podobně jako dobrý žebříček doporučení.
  • Latency znamená, jak dlouho uživatel čeká na odpověď.
Aktuálně: Pokud potřebujete porovnávat chování modelu dnes, použijte Query v RAG mode a No RAG mode a výsledky ukládejte ručně exportem do Markdownu nebo PDF.

Dashboard admin / curator / analyst

Dashboard otevírá přehled stavu WebRAGu v Grafaně. Pomáhá rychle vidět, kolik je v systému zdrojů a dokumentů, jestli se zpracování daří a jestli vznikají incidenty.

Pro běžné pokládání otázek Dashboard nepotřebujete. Je užitečný hlavně pro lidi, kteří se starají o obsah nebo provoz systému.

Audit & Access admin

Admin část obsahuje odkazy na auditní logy v Grafaně a správu přístupu v Keycloaku. Auditní logy slouží ke kontrole důležitých akcí, jako jsou přihlášení, změny zdrojů, spuštění ingestu, dotazy a generování API tokenů.

Role se spravují v Keycloaku. Frontend kontroluje změnu role každých 30 sekund a při změně si obnoví token.

WebRAG User Documentation

WebRAG lets you ask questions over web content that has been collected and indexed by the system. In normal use, you log in, ask a question, and receive an answer with citations that point back to the source material.

How to Log In all users

The login screen can show one or two login methods depending on server configuration.

OIDC / Keycloak Login

  1. Click Sign in with OIDC.
  2. Your browser opens Keycloak.
  3. If Keycloak shows a Google option, click it.
  4. Sign in with your normal account.
  5. After success, you return to WebRAG.

This is the normal login method for users. Session persistence is controlled by Keycloak.

Local First-Admin Login

The local password is mainly for initial setup or emergency administration. You enter only the password, not a username. This login lasts only for the current browser session.

Roles

RoleWhat the user can do
webrag_userUse Query and manage a personal REST API token.
webrag_analystUse Query, Knowledge Base, Experiments, and REST API.
webrag_curatorManage sources, pipeline jobs, incidents, Knowledge Base, Query, and REST API.
webrag_adminAll features, including audit logs, Keycloak administration, and selected delete actions.

REST API Access all users

Use a REST API token when you want to call WebRAG from a script, terminal, or another tool. Open REST API Access, click Obtain API Token, and store the token immediately.

  • The token is shown only once.
  • The server stores only its hash, not the readable token.
  • If you lose it, click Regenerate. The old token becomes invalid.
  • Send it as Authorization: Bearer <WEBRAG_API_TOKEN>.
export WEBRAG_URL="https://webrag.example.com"
export WEBRAG_API_TOKEN="paste-token-here"

Replace WEBRAG_URL with your deployment URL. If your environment exposes API routes under /api, add that prefix before the endpoint path.

Check Your Token

curl -s "$WEBRAG_URL/auth/me" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"

Query all users

Query is the main screen for asking questions. In RAG mode, WebRAG first finds relevant parts of indexed documents and then asks the language model to answer from that material. The answer includes citations so you can inspect the evidence.

Modes in the UI

ModeMeaning
RAG modeNormal mode. Searches indexed documents and answers with citations.
No RAG modeSkips the knowledge base. Useful for comparison.

Automatic Search Fallback

keyword_fallback means WebRAG temporarily used simpler text search because the regular search was unavailable or did not find enough evidence. The answer may be less precise, so always check the citations.

Important Options

  • Strict Grounding tells the model to answer only from retrieved documents. When it is off, the answer is relaxed and may include general model knowledge outside retrieved documents.
  • top_k is an API argument for how many chunks to retrieve. Default is 5. Higher values give more context but may be slower.
  • source_id is an API argument that restricts search to one source.

Choosing a Model Provider

By default, WebRAG uses the model configured on the server. If you need to try another compatible model for one request, open Pass Values for Your Own API on the Query screen.

  • Provider can be Default, OpenAI, or OpenRouter.
  • Base URL is the provider API address. The help button offers ready-made examples.
  • API Key is used only for the current request and is not stored.
  • Model Name is the exact model name at the provider, for example gpt-5.5 or openrouter/auto.

The same settings are available through the API fields upstream_provider, upstream_base_url, upstream_api_key, and upstream_model.

After new documents are added, it can take a short time before they are fully used in answers.

API Example: Ask in RAG mode

curl -s -X POST "$WEBRAG_URL/query/" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "question": "What sources are indexed?",
    "mode": "rag",
    "top_k": 5,
    "strict_grounding": true,
    "source_id": null
  }'

API Example: Ask in No RAG mode

Knowledge Base admin / curator / analyst

Knowledge Base shows documents that WebRAG has already collected and split into smaller parts called chunks. Each chunk can be used as evidence for Query answers.

What You Can See

  • Document, chunk, source, and embedding readiness counts.
  • A table of documents with URL, ingest strategy, quality, and ingest time.
  • Chunk details for a selected document.
  • Stored Markdown and screenshot evidence links when available.

Admins and curators can delete documents. Deletion removes the document and its parts from search.

Sources admin / curator

htmlFetches plain HTML without JavaScript. Fast for simple static pages.
renderedUses a headless browser. Useful for JavaScript-heavy pages.
screenshotCaptures a screenshot and uses a visual model to read it. Most expensive fallback for difficult pages.

Pipeline / Jobs admin / curator

Pipeline shows ingest system activity: pending jobs, active workers, 24-hour error rate, and job history. A job is one attempt to fetch and process one URL.

Incidents admin / curator

An incident is created when the scraper meets a CAPTCHA, rate limit, or access block. The goal is not to bypass it silently, but to tell a human that the source needs attention.

Working With Incidents

  • Resolve closes the incident with a note and automatically queues a retry job.
  • Whitelist in the UI is a quick resolve action with a prepared note.
  • Admins can create a test incident through /incidents/simulate.

API Examples

curl -s "$WEBRAG_URL/incidents/?status=open&limit=20" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN"
curl -s -X POST "$WEBRAG_URL/incidents/INCIDENT_ID/resolve" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"resolution_note":"Checked the source; access is available again."}'
curl -s -X POST "$WEBRAG_URL/incidents/simulate" \
  -H "Authorization: Bearer $WEBRAG_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"url":"https://example.com/captcha-test","severity":"medium"}'

Experiments admin / analyst

Experiments are planned for comparing answer quality. In the current version, the frontend shows a placeholder and backend endpoints are not implemented yet.

The goal is to take a set of test questions and measure whether WebRAG found the right evidence quickly and in the right order.

  • Recall@k says how many correct pieces of evidence made it into the short result list. Think of checking whether you pulled all important books from a shelf.
  • MRR tracks how soon the first good result appears. The ideal case is that the first result is already useful.
  • nDCG measures whether the best results are near the top, like a well-sorted recommendation list.
  • Latency means how long the user waits for the answer.
Currently: To compare behavior today, use Query in RAG mode and No RAG mode and save results manually with Markdown or PDF export.

Dashboard admin / curator / analyst

Dashboard opens a Grafana view of WebRAG health. It helps you quickly see how many sources and documents exist, whether processing is succeeding, and whether incidents are appearing.

You do not need Dashboard for normal questions. It is mainly useful for people who maintain content or operate the system.

Audit & Access admin

The admin section links to audit logs in Grafana and access control in Keycloak. Audit logs help review important actions such as logins, source changes, ingest triggers, queries, and API token generation.

Roles are managed in Keycloak. The frontend checks for role changes every 30 seconds and refreshes the token when needed.
